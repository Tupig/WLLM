# 严格开发流程（PROCESS）

每个功能单元必须走完六步，**不允许跳步，不允许并行糊弄**：

```
① 调研  →  ② 测试  →  ③ 落盘  →  ④ 审查  →  ⑤ 测试  →  ⑥ 验收
```

## 各步定义与出口条件

| 步 | 做什么 | 出口条件（不过不进下一步） |
|----|--------|---------------------------|
| ① 调研 | 读本仓相关代码 + 查 git 历史与同类开源实现，写清"怎么做、边界是什么" | 有明确设计：输入/输出/错误路径/参照实现 |
| ② 测试 | **先写测试**（vitest），此时必须红或覆盖新行为 | 测试文件落盘、跑一次确认按预期红 |
| ③ 落盘 | 最小实现让测试转绿；只改本功能相关代码 | `npx vitest run` 相关用例绿 |
| ④ 审查 | 自审 checklist：正确性/边界/错误路径/安全（注入、路径逃逸、命令盲执行）/与 AGENTS.md 约定一致/无死代码 | 审查点写进提交信息（必须留痕） |
| ⑤ 测试 | 全量回归：`npx tsc --noEmit` + `npx vitest run`（如仍有 shell 源再加 `bash -n`） | 全绿，无回归 |
| ⑥ 验收 | 对照该功能验收标准逐条核对（AC 清单），留验收结论 | AC 全过 → todo 标 completed |

## 规则

- **② 在 ③ 之前是硬性的：没有测试文件不许改代码**

## Bug / 优化 · Issue 强制流程（2026-09-30 起）

本地发现的**任何 bug 或优化点，必须先上报 GitHub issue，再动手修**：

1. **上报**：`gh issue create -b "<现象/根因/影响面/复现方式>"` —— 未建 issue 不许改代码
2. **修复**：提交信息必须引用 issue 号（`fix #<N>: ...` 或 `perf #<N>: ...`）
3. **关闭**：⑤ 回归全绿 + 推送后 CI 绿 → `gh issue close <N>`（关闭时留一句修复摘要）

新功能开发走六步流程；bug/优化在六步之外**必须**先过本节。issue 是唯一追踪载体，
工作区不留待办文档；查历史 bug 用 `gh issue list --state all`。

- ④ 发现问题 → 回 ③ 修，重新走 ⑤
- ⑤ 红了 → 回 ③ 修，重新走 ⑤（不许改测试将就实现，除非测试本身错误且有据）
- ⑥ 不过 → 该功能不算完成，todo 不标 completed
- E/F/I/G 类全六步

## 记录

每个功能的 ④审查 与 ⑥验收 写入**提交信息**（简短即可：审查点、发现问题、AC 结果）；
历史文档不落盘，查过往决策用 `git log`。
